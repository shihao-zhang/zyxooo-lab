依赖与反馈

这些关系表达判断之间的约束，不要求六篇依次交付，也不把 02、03、04 视为互不影响的并列项。

  • 01 → 02、03、04，并直接连接 06。 决策目标、被测对象与约束既限定评测，也限定结果的使用。
  • 02 → 03、04。 允许的结果约束判据；需保留的初态、观测与动作语义约束执行。03 也向 02 反馈可评分性限制；需检查这是否使任务偏向容易自动评分的工作，不能把便于评分当作入选的唯一标准。
  • 03 ↔︎ 04。 判据提出证据需求，采集能力限定实际可得的证据；证据不足时需共同修正约定。
  • 02、03、04 共同支撑 05 → 06。 样本边界、判分有效性与实际执行条件共同限定比较、归因和外推；06 再判断结论能支持什么行动。
  • 06 → 01、02、03、04。 新事实可能要求重定目标、补充样本、修订判据或重查执行条件，再据此更新结果解释。

本篇判断：Agent 评测应先明确“这份证据要改变什么决定”，再界定被测系统，最后选择能力维度与指标。 模型能力、Agent 配置表现和业务收益不能相互替代。本篇研究三者怎样连接，不展开任务采样、裁判实现、运行器、统计检验和上线实验的完整方法。以下研究事实来自一手材料；标为“本文建议”的部分是综合推断，未做真实运行或业务验证。

一、第一性：评测购买的是决策信息

假设团队拿到“任务成功率 85%”。它不能独自回答是否值得购买、能否放开写权限，或者应先改善模型还是工具。还缺少成功的任务是什么、谁完成了剩余工作、允许付出多少成本，以及错误会造成什么后果。

因此，评测的最小单位不应只是一个分数，而应是一个带条件的判断：对于某类工作，在规定信息、权限、资源和人工参与下，方案 A 相比基线 B，是否更符合某项产品目标。 这不是要求每次都做全系统研究，而是要求证据与决定相匹配。一次廉价诊断可以支持“值得继续试”，却未必足以支持“可以替代人工”。

本文建议同时列出候选行动，以及什么结果会改变决定。例如，候选行动是维持建议模式、扩大受限试用或允许授权后执行；触发条件可写成“关键约束达标、目标结果达到业务所需改善、人工负担未超出可接受范围”。具体门槛及证据强度由业务责任人与评测设计共同确定，并保留“证据不足，继续验证”的分支，不能等看完分数再临时调整。

《AI Agents That Matter》明确区分模型研究与下游选型：前者可能关心计算投入和能力的关系，后者需要考虑实际支付成本与任务表现。作者同时主张联合观察准确性和成本，反对只追求最高分。本篇采纳的是这种问题区分，不把论文中的历史价格当成今天的采购依据。原论文，§2、§4

要改变的决定 评测需要回答什么 证据不能越过的边界
是否换模型 在相同任务与可比配置下，候选模型是否改善目标表现？ 结论先限于测试过的配置，不能直接称为模型的普遍优劣。
是否改 Agent 方案 新工具接口、记忆或流程是否改善目标表现，代价是什么？ 不能把整个方案的改善全部归给底层模型。
是否扩大业务使用 包含人工接管的整体流程，是否比现有方式更有价值？ 离线完成率只能支持价值假设，不能证明业务收益。

这些问题常同时存在，但应分别记录答案。否则团队可能用便宜模型的单次调用费用证明流程省钱，或用少数难题的突破证明可以全面自动化。

二、被测对象：模型、Agent 配置与完整系统

模型是产生预测或行动建议的核心组件；Agent 配置决定它如何获得信息、选择行动并持续工作；完整系统还包含真实服务、人和组织流程。 这是一种服务于评测设计的分层，不是唯一的架构分类。

Anthropic 在 2026 年的评测文章中，将 Agent harness 定义为使模型能够处理输入、编排工具并返回结果的系统，并强调评测 Agent 时测的是模型与该系统的组合。它还区分对话记录与最终环境状态：声称订好了机票，不等于数据库里真的存在预订。本篇据此要求同时说清“谁在行动”和“什么算交付”。官方技术文章：评测结构

被测对象 必须讲清的组成 合适的结论表达
模型在指定条件下的表现 模型版本、输入信息、调用方式与推理预算；外围策略尽量保持可比。 “在本工具与提示配置下，替换模型后表现如何。”
Agent 配置 模型、提示、知识与记忆、工具及权限、控制流程、重试与停止规则。 “这套可部署配置在规定任务和预算下表现如何。”
完整业务系统 Agent 配置，加上服务可靠性、人工审核与接管、用户操作及交付流程。 “这套人机流程在规定业务范围内产生什么结果和代价。”

同一个功能也可能在不同研究中处于不同位置。若研究工具接口设计，接口是被测方案的一部分；若研究模型替换，接口通常应固定。若研究业务服务中断时的交付能力，服务故障属于测试条件；若只想了解模型推理能力，混入随机服务故障会妨碍解释。边界由问题决定，不能只按软件模块命名决定。

固定配置也有取舍：原有提示和工具格式可能已经围绕旧模型优化，直接替换会使候选模型处于不利条件。若决定是“能否直接替换”，应把结论限定为现有配置下的效果；若决定是“充分适配后选哪套方案”，可给各候选同等适配预算，记录改动、投入和评测条件，此时比较的是适配后的组合系统。两类结果应分别呈现。

一个现实例子是 SWE-agent。作者在固定语言模型的前提下研究 Agent–Computer Interface，调整命令、反馈和历史信息的呈现，并通过消融分析这些设计的影响。这表明“同一个模型”不等于“同一个被测 Agent”；接口也可能成为能力瓶颈。本轮核对论文机制，未复现其性能提升。SWE-agent，§2、§5.1

本文建议保留一张简短的“被测对象说明”：名称与版本、包含什么、外部条件是什么、允许谁介入、资源上限是什么。换模型、开放新权限或改变接管规则后，应更新说明。这样才能判断下一份分数是在比较版本，还是已经换了产品。

短案例：当 Agent 本身成为交付物

Hyper-τ（τ^τ-bench）把“构建客服 Agent”设为任务。外层 Developer 是模型与编码 harness 的组合：它从政策文档、客服记录等材料恢复需求；在启用客户访谈的任务中，还需向模拟委托方 Client 追问遗漏的信息，再提交可执行 Agent。这些企业式材料由领域规则转换构造，并非真实客户项目的原样记录。论文 §3.1–3.2

内层让交付的 Agent 服务模拟终端用户，在 Developer 未见的任务上检查最终状态与沟通结果；外层得分由这些表现及服务超预算惩罚决定。因此，被比较的是构建系统，接受运行验收的是它交付的 Agent。需求访谈中的 Client 与验收中的用户承担不同角色，不能把访谈顺利或代码能运行当作交付成功。官方 README

构建预算与服务预算也要分开：前者约束开发阶段耗时，并另记 Developer 调用成本；后者约束交付 Agent 平均每次对话的额度及可用模型。本文据此建议同时看“花多少投入造出来”和“造出的系统怎样交付”。该基准支持受控模拟下的构建能力比较，尚不能证明真实客户收益。论文 §4

三、2024—2026：问题从“能做”扩展到“怎样才有用”

这不是后一种评测取代前一种，而是不同研究逐步补上缺失的业务条件。

2024 年的 τ-bench 将用户对话、领域规则和工具操作放到同一任务中。Agent 既要理解用户意图，又要遵守规则并改变目标状态。它提出 pass^k，以多次尝试全部成功的概率观察一致性，说明平均完成率之外还存在“能否稳定交付”的问题。τ-bench，§3、§5

2025 年的 τ²-bench 进一步引入双方都能操作环境的电信支持场景。作者比较了 Agent 独自控制全部工具与引导模拟用户共同操作的设置，报告后者表现下降。这使“自己会做”与“让用户配合做成”成为可区分的问题。不过，两种设置也改变了信息与控制条件，不能把全部差值理解成纯粹的语言沟通能力差异。τ²-bench，§4.2

同在 2025 年，METR 用人类完成任务所需时长，描述 Agent 在指定成功概率下能处理的任务跨度。这个量提供了理解任务复杂度的另一种尺度，但它既不是 Agent 自己的运行时长，也不是已节省的人类工时，更不是一个岗位可自动化的比例。METR 时间跨度研究

到 2026 年，Anthropic 的方法总结更明确地将自动评测放进包含生产监测、人工审阅等证据的整体框架。本文的综合判断是：产品规划需要同时看任务能力、交付条件和实际价值，而不是期待一个更大、更难的排行榜解决所有问题。这是方法性建议，并非对全部行业实践的普查结论。Anthropic 方法总结

四、从业务价值推导能力，而不是从能力清单猜价值

以下是教学假设：企业准备引入售后退款 Agent。业务目标是缩短处理周期，同时控制错误退款，并降低坐席总投入。现状由人工处理；拟上线范围只覆盖规则明确的部分退款请求，争议和权限不足的情况仍交人工。

可以按“价值目标 → 工作结果 → 必要能力 → 可观察指标”倒推。例如，“降低坐席投入”要求 Agent 不仅判断退款是否成立，还要取得必要确认、正确执行，并把不能完成的事项交接清楚。单独测规则问答答对率，会漏掉执行和接管造成的工作量。

业务目标 必要能力或工作结果 候选观测指标
降低人工总投入 能独立完成适用任务，也能给人工提供可接续的信息。 每件来单的人工处理、审核与返工时间，以及自主完成覆盖率。
控制错误退款 能确认身份、判断资格，并在授权边界内执行。 不当退款、错对象或错金额的发生情况；严重违规单独记录。
缩短处理周期 能补齐信息、执行操作并及时接管。 从来单到确认解决的时长分布；等待用户与等待人工分别记录。
保持问题真正解决 能交付正确结果，而非仅结束对话。 在约定观察窗口内的复联、重开与结果验收情况。

这些指标是待验证的设计建议，不是已证明的行业标准。每个指标需要写清分母和口径：自主完成率若只统计 Agent 选择接手的简单单，会掩盖覆盖范围；只统计成功单的成本，会隐藏失败、重试和人工补救；平均耗时下降，也可能伴随少数客户等待显著变长。

能力指标主要帮助解释和诊断，业务指标才接近价值目标。规则理解正确，不保证工具执行正确；工具执行正确，也不保证客户问题得到解决。反过来，一次业务成功可能由人工挽救，不能据此认定 Agent 已具备自主能力。至少应区分“Agent 独立完成”“人机共同完成”“未完成”，并记录必要的接管负担。

若要把价值折算为经济账，本文建议先建立同范围的比较口径：相对基线增加的合格交付价值与节省的资源，扣除新增运行、审核、返工和维护代价。 各项不能重复计算，也不宜把难以可靠估计的重大违规损失强行折成一个权重。对这些约束先设门槛，再比较门槛内的成本和效率；门槛由业务责任人确定，本篇不凭空给数值。

五、三个容易改变产品路线的机制对照

1. 找到一次解，与每次可靠，是两种产品承诺

pass@k 关心 k 次尝试中至少一次成功；pass^k 关心 k 次尝试全部成功。在 τ-bench 的定义里，它们针对同一任务的独立重复尝试，再跨任务汇总。二者不能互换，更不能把全体任务平均成功率简单取 k 次方，代替真实的一致性估计。τ-bench 指标定义

本文推断：允许生成多份候选、且能低成本筛选正确结果的产品，可以重视搜索式成功；直接修改订单的产品更需要每次执行都可靠。即使 pass@k 很高，也仍需证明产品能识别那个正确答案，并计入选择与重试成本。不能把离线裁判替产品完成的挑选工作视为免费能力。

2. 自主程度更高，不保证用户价值更高

Agentless 使用预先组织的定位、修复、补丁验证流程，而非让模型自由选择所有后续行动。作者在当时的 SWE-bench Lite 设置中报告了有竞争力的效果与成本。这是保留简单工作流基线的理由，不是“固定流程永远优于 Agent”的证明；本文也不据此推断 2026 年的排名。Agentless，v2，§3、§5

本文建议比较三类实际可行基线：现有人工流程、规则或固定工作流，以及更自主的 Agent。若流程稳定、例外少，固定步骤可能更容易管理；若需要依据反馈不断调整路线，自主机制才更可能带来额外收益。选择依据应是任务适配和整体结果，不能把工具调用次数、多 Agent 数量或“自主完成”标签本身当成价值。

3. 能力进步，不自动等于工作提速

METR 在 2025 年发表的随机对照实验，研究了 16 名熟悉各自开源项目的开发者和 246 项实际任务。作者报告，在其早期 2025 年工具与实验条件下，允许使用 AI 的任务耗时反而增加 19%。这是特定人群、项目与时期的结果，不支持“AI 普遍降低生产力”的结论。METR，2025 年研究

时效边界同样重要。METR 在 2026 年 2 月更新中认为，开发者不愿参与无 AI 条件、选择性提交任务以及并行使用 Agent 的计时问题，使后续数据难以可靠估计当时的收益。作者认为加速可能增加，但对增幅证据较弱。因此，既不能沿用旧结果否定今日工具，也不能把后续原始估计说成已证明普遍提速。METR，2026 年实验设计更新

本文据此强调：业务系统的测量对象必须包含人。生成得更快可能增加审核负担；自主成功不高的辅助工具，也可能通过帮助人处理某个瓶颈而产生价值。这两种关系都应作为待检验假设。

六、产品规划真正应带走什么

首先，把“希望 Agent 更强”改写成一个近期决定。例如“是否把规则明确的退款从草拟建议升级为授权后执行”。这会自然暴露需要测量的新能力：从答对，扩展到执行正确、遵守授权以及出错后可接管。

其次，把业务目标与能力假设分开写。目标可以是降低坐席总投入；假设可以是更好的信息收集减少追问、更完整的交接降低人工接手时间。假设必须允许被推翻：如果问答准确率提高但人工投入未降，应检查价值链的其他环节，而不是继续堆同一种能力指标。

再次，先保留结果、成本、时效、人工负担和关键约束的分项信息。只有确定取舍规则之后，才考虑汇总。一个总分把严重违规与节省几秒钟互相抵消，通常会让决策更难解释。具体业务也可能接受不同方案：低频高价值任务容许更高运行成本，高频低风险任务更关心单位经济性。

最后，每项结论都写明适用范围。测了模拟退款任务，就报告该设置下的表现；验证了某模型与某工具组合，就报告该组合。明确范围不是削弱证据，而是让团队知道下一笔验证投入应补在哪里。

先建立一个判断：约束失真时，增加任务数量不能弥补代表性

企业评测不能只问“题目像不像工作”，还要问“做对这道题，需要面对的条件，是否与目标业务相同”。如果真实采购需要核对合同版本、发现重复订单、取得批准，而评测直接给出正确供应商和批准信息，那么任务即使在真实采购软件里成功执行，也只证明了后半段操作能力。

本篇把代表性拆为两个问题。覆盖是目标场景中哪些类型进入了样本；保真是进入样本的任务保留了哪些关键约束。前者需要一个可说明的采样范围，后者需要逐步解释转译过程。生态效度在此指评测中的行为和结果，对真实工作情境有多大解释力；不是画面相似度，也不是一个脱离用途的统一分数。这是本文的分析框架，不是某个基准的官方分类。

可把整条证据链读成：业务范围 → 原始工作证据 → 任务抽象 → 环境实例 → 人工复核 → 适用范围声明。每次转换都可能丢东西：访谈会漏掉习惯性判断，日志未必记录线下协调，模板会合并例外，模拟器会改变可见信息。研究的核心是把这些变化显式留下，而不是追求一比一复制企业。

二、工作证据怎样变成任务：三种入口应当相互校正

真实记录：保留发生过的困难，但先问记录遗漏了谁

工单、操作日志、产物版本和审批记录，可以提供真实输入、发生顺序及业务结果。但日志里的“先查 A，再改 B”未必说明为什么这样做；成功结案记录也可能缺少被放弃、转交或线下解决的任务。本文建议先定义业务范围和时间窗，再按任务族、角色、结果与异常类型抽样；把“没有留下可用记录”单列，避免把数据容易取得误认为业务重要。

SWE-Lancer 提供可复核的历史工作转译案例：任务来自 Expensify 在 Upwork 发布并由付费贡献者解决的工作，使用原问题描述及修复前代码状态，再补建端到端测试。真实来源没有消除选择边界：它仍围绕一个代码库和自由职业工作机制。本篇借鉴其“历史问题与当时状态成对保留”的方法，不把其结果外推到一般企业岗位。SWE-Lancer §2.2

访谈与专家：补回判断依据，但不能替代发生频率

访谈应围绕具体事件追问：当时知道什么、缺什么、为什么没有采用另一个方案、什么情况下必须停下。业务专家能识别日志没有表达的权限、例外和责任；“资深人士认为典型”仍是专家判断，不能直接写成“覆盖大部分工作量”。因此任务来源应区分真实记录、访谈复述、专家重建和作者假设。

SCUBA 共含 300 个任务实例：从真实 Salesforce 用户访谈获得用例，并关联 Trailhead 知识文章；每个模板填值产生五个查询，再由 ChatGPT 改写、作者检查。环境还会合成记录、配置权限。这是“真实用例来源—模板变体—合成初态”的混合链路，不能视为三百条原始用户会话。SCUBA §3.2–3.2.2

关于如何把需求追问本身纳入构建任务，参见 01 篇 Hyper-τ 短案例；其中的模拟委托方访谈不能替代真实业务访谈证据。

模板与合成：扩大变化范围，不能凭空扩大现实证据

模板适合固定业务关系、改变实例参数，例如保留“合同额度约束订单”的关系，替换金额与日期。仅换姓名主要增加表面变化；增加规则冲突、资料缺失、权限差异，才可能扩展决策条件。反过来，任意组合异常也可能制造现实中不会同时成立的任务。

SaaS-Bench §3.2 的承重点是两层生成：先生成场景、目标和跨应用依赖，再绑定具体入口、数据状态与素材；两层均由模型生成，人工挑战、审查并修订。静态检查还关注跨应用自然性、parallel tasking 与规格堆叠。本文据此推断，生成质量应复核“约束是否保留、依赖是否自然”，而非只数步数或软件数量。SaaS-Bench §3.2

三、环境需要多真实，取决于要测哪种能力

为了研究业务推理，可以用简化 API；为了研究页面定位，必须保留相关界面；为了研究沟通协作，则需要另一个参与者的知识与行动边界。环境选择应跟随被测能力。本文建议每项简化都写出“保留了什么、删除了什么、因此不能声称什么”。

环境选择 适合保留的条件 需要单独证明的部分
规则与 API 模拟 状态变化、权限检查、规则依赖。 工具语义与真实系统是否一致；界面操作能力不在其中。
真实软件的开发或沙箱实例 页面结构、原生字段与应用行为。 客户定制、数据规模、集成和业务分布是否匹配。
自建跨应用工作场景 对象关系、文档线索和协作依赖。 作者设定是否反映目标组织，而非理想化工作方式。
模拟用户或同事 分散信息、追问与协同行动。 模拟者是否过度配合、泄露信息或偏离角色。

τ-bench 明确简化现实领域的数据库、API 与政策，并迭代人工任务，使用户指令对应唯一结果。这样有利于可判定性，却有意减少了业务歧义。若产品要帮助客户澄清互相冲突的目标，这类任务只能覆盖其中一部分；不能把所有歧义消除后，再声称测到了处理歧义的能力。τ-bench §4、附录 B

τ²-bench 又揭示另一种简化：用户不只是回答问题，也会操作设备。它给用户和 Agent 各自的工具与观测，并用环境状态约束模拟用户。这为故障排查引入了协同行动，但仍是受控模拟；模拟器一致性检查不能证明真实客户具有相同的理解力、耐心和执行行为。τ²-bench §3、§4.3

四、覆盖不是数量：至少分别看任务族、约束和目标分布

WorkArena++ 的 682 项任务对应 341 个工作流的两种呈现层级；附录 D 又按能力分桶，减少类似交互的冗余。这个例子说明，实例数、工作流数、能力条件数应分别报告。大量相似实例有助于检查稳定性，不能自动变成同样多的独立业务覆盖。WorkArena++ §3.1、附录 D

本文建议维护两份视图：一份按真实业务中的出现情况描述常见任务，另一份单列低频但后果严重的挑战条件。前者回答日常适用性，后者回答边界脆弱点。没有可信频率时，就报告所见样本及覆盖空白，不把人为均衡的任务集称为“企业日常通过率”；如何加权和估计不确定性归第 05 篇。

GDPval 从行业和职业向下组织任务，以真实工作产物或按其类似构造的产物为基础，由专家检查职业相关性；并非凭空编题。官方来源说明 但其初版仍排除大量隐性知识、专有工具访问与人员沟通，通常一次提供完整上下文。因此“覆盖若干工作交付物”与“覆盖整个职业”仍须分开。GDPval §5

还有一个容易忽视的循环：先限定只有能自动评分的任务才能入选，最后就会得到一个偏向可评分工作的任务集。TheAgentCompany 主动承认这一限制，并指出没有覆盖产品创意、系统架构等更复杂创造性任务。对于难以自动评分但业务重要的任务，合理做法可以是保留专家评审成本，并把判据问题交给第 03 篇，而非默默删去整个任务族。TheAgentCompany §8

五、教学例：怎样把“采购异常处理”变成可研究的任务族

以下是内部探索用的虚构案例，没有对应客户证据，也不是产品需求。假设业务要处理“供应商要求提前付款”这类请求，验收记录缺失是其中一种变体。目标是研究 Agent 能否识别条件、补齐必要信息并采取恰当动作，而非只测建单。

从原始请求、当时合同与验收记录出发，用访谈补齐批准规则，再形成下列四种虚构覆盖变体。每种都需保留对应初态与可见信息，不能提前透露事后事实。

变体 测到的关键约束 合理处理方向
条件与材料齐备 付款条件成立且经办权限充分。 核对后按授权办理。
验收记录缺失 必要证据未齐，不能自行补造。 暂停付款并请求补证。
合同版本冲突 金额或期限依据存在冲突。 查明有效版本后再处理。
无例外批准权限 提前付款须由其他角色批准。 提交有权者，不越权执行。

未覆盖供应商身份欺诈和银行到账延迟：前者需独立身份核验资料，后者需异步支付状态，本例未构造。四种变体也不代表真实发生比例。

专家解释决定业务判断的条件，环境团队核对其如何变成可见信息和状态变化。先复核一个小任务族，再讨论扩大投入；这里不预设产品形态。

若只把“付款成功”当作目标，发现缺证后正确停止也会被错记为失败。公开研究已有对应设计：WorkArena++ 附录 C.5 要求 Agent 识别无法执行的指令并通知用户，例如不存在的字段或无效商品配置。这支持把正确不执行纳入合法结果，但不直接验证本例的采购规则。WorkArena++ 附录 C.5 判据与初态一致性分别归第 03、04 篇。

六、带着什么证据，才可以开始使用这批任务

本篇建议每个任务族附一份简短说明：它面向哪个组织或角色，原始证据是什么，哪些内容由作者合成，专家具体复核了什么，哪些条件被简化，哪些场景尚未覆盖。人工执行只支持“在指定环境中可完成”；业务专家复核支持“具有场景合理性”；只有目标业务中的对照证据，才能进一步支持迁移判断。三者不能相互替代。

做对与做错，能被正确识别吗？

判据与裁判有效性

裁判也需要校准。合理替代解可能被误拒，错误结果也可能钻过判据。

核心判断：可信评分需要同时证明两件事——规则代表了任务真正要求，裁判能根据足够证据正确执行规则。 更强模型、更详细的评分表、更多裁判投票，都不能自动补上其中任何一环。工程上可先用程序核验可确定的事实，再用明确判据处理开放质量；对未知、冲突和故障保留独立出口，并用正确变体与错误反例检验整个评分系统。

本篇假定任务范围、可用能力和运行条件已经约定，只回答“同一份交付凭什么算完成”。任务代表性归第 02 篇，证据怎样可靠采集归第 04 篇，分数差异的统计推断归第 05 篇，是否据此选型或发布归第 06 篇。正文的论文结果均为作者报告；标明“本文建议”的框架与教学例是研究综合，不是原论文结论。本轮核验公开一手材料，未运行基准、未测裁判，也未读取内部 PDF。

一、先分清判据、裁判与证据

判据规定什么值得得分，例如“所有重复订单只保留一条，原始金额不变”。裁判是执行判据的机制，可以是 SQL、测试程序、模型或专家。证据是它实际看见的文件、状态、轨迹与来源。rubric 是评分规则，不是与程序、模型、人类并列的第四种裁判；同一 rubric 可以交给不同执行者。Anthropic 的工程总结也区分代码、模型、人类三类 grader，并允许一个任务组合多个 grader。Anthropic，2026-01-09

本文把目标表述为：在任务允许的解法集合内，尽量接受功能等价的正确结果；对越过任务底线的结果，尽量拒绝。前者对应误拒，后者对应误放。稳定执行错误规则，只证明可靠性，不证明有效性；重复打出同一个分数，不代表这个分数回答了用户的问题。

例如，要求“合并两份客户清单”，可能允许不同排序与列宽；要求“保留可更新的公式”，则静态数值相同仍可能不合格。合理解法集合必须由任务语义限定，不能由参考答案的偶然格式限定，也不能为减少误拒而无限放宽。任务存在歧义时，先澄清或保留多种可接受解释；不能让隐藏测试偷偷增加义务。

这不是裁判强弱排行榜。程序善于精确执行规则，却不会自动知道规则错了；模型可处理语义差异，却可能不会识别专业错误；专家可解释争议，但也可能共享盲点。本文建议先明确“什么证据能够推翻通过结论”，再选择最便宜且已验证能识别它的机制。

对于开放质量，rubric 应描述可观察条件和边界例。例如把“报告专业”拆为“关键结论有来源”“来源确实支持该结论”“不确定事实未写成确定结论”。每项保留证据位置、通过/失败/未知及理由。拆分要以区分实质错误为目的，不按措辞扩充条数；“表达清晰”“易读”“组织良好”可能反复奖励同一属性。

三、2024—2026 年的变化：从使用裁判，到检验裁判

1. 判断偏好，不能代替判断正确

JudgeBench 于 2024 年提出、2025 年修订，使用同一模型生成的正确与错误答案构造困难配对，覆盖知识、推理、数学和代码。其 GPT-4o 主集合含 350 对；GPT-4o 配 Arena-Hard judge 提示的 56.57%，指按论文聚合协议选中正确答案的配对比例。每对换序判断两次：偏好同一答案，或一次偏好、另一次平局时，按该偏好判定；两次偏好冲突或两次平局均计错。普通单次二选一随机猜测的 50% 可作直观参照，但不能直接当作这一换序聚合协议的随机基线。这说明“擅长生成、受人喜欢”不等于“擅长找出细微错误”，但不能把旧模型、特定题集上的分数当作今天全部裁判的上限。JudgeBench v2，§3–4

CALM 的偏差研究则通过受控修改检查判断是否随无关因素变化，包括答案位置、篇幅及权威暗示。其研究报告不同模型对这些扰动的敏感程度不同。本文据此采用一个检验思路：内容正确性没有改变时，判断应尽量保持；关键事实被改变时，判断应随之变化。匿名化、换序和异构模型是待验证的缓解手段，不能直接当作消除偏差的证明。Justice or Prejudice? v2，§2–4

2. 确定性测试，也要接受有效性审计

OpenAI 在 2026 年审计了 138 道 SWE-bench Verified 题：它们来自 o3 在 64 次独立运行中未能稳定解决的题目，每题由至少六位工程师独立审查，问题再复核。作者报告 59.4% 存在测试或描述的实质问题。其中一个例子是测试导入题目未要求的 get_annotation，使其他功能正确的实现因名称不符而失败。59.4% 的分母是有选择偏差的 138 题，不能推广为全部 500 题的缺陷率。OpenAI 官方审计，2026-02-23

OSWorld-Verified 在 2025 年的修订提供另一种路径：维护者列举等价电子表格公式被误拒、段落间空行格式存在合理变体等问题，并通过扩充可接受结果、调整格式和颜色容差改进评分，强调优先修裁判而非改任务。这里讨论的是该版修订，不是对后续 OSWorld 版本质量的总评。它提示我们：参考产物最好用于证明至少一种解法成立，而非规定唯一产物。XLANG 修订报告

3. 更细的 rubric 需要更细的元评测

2026 年的 RRD 研究把 rubric 生成拆为递归细化、过滤错向与冗余项、降低相关项目的重复权重。作者在引言中指出，未经筛选的生成式 rubric 可能使判断准确性退化；规则质量与聚合方式需要分别验证。本文只采纳“规则质量和聚合方式需要验证”这一机制启示，不把作者在 JudgeBench、PPE 等设置中的改进外推为企业 Agent 的已验证收益。RRD v1，§1–3

RubricEval 进一步直接评估“一个回答是否满足一条 rubric”。其 3,486 条样本经模型筛选与仲裁产生；作者随机抽查 160 条，以两位人类独立标注并讨论分歧，报告人与自动标签一致率 85.0%。这既提供条目级核验方法，也暴露元评测标签自身仍有不确定性。多裁判一致不等于独立真值，特别是裁判还参与了标签生成时。RubricEval v1，§3.3–3.4

这条演变线是本文对所选材料的综合：评测重心逐步从“选一个好裁判”，扩展到检查题目、评分规则、标签生成和裁决流程。不同方法并未形成可以互相替代的统一标准。

四、教学例：一份订单异常报告应该怎样判

以下是本文构造的教学例，未经实测。任务要求：“合并两份订单表，按订单 ID 去重；冲突记录单独列出；金额保留两位小数；生成异常说明并附订单依据；不得修改原表。”设定允许不同排序、不同版式，但金额计算必须正确。

首先检查事实。程序比较输入与输出的订单集合、金额计算、冲突条目和原表内容；两位小数要明确是展示要求还是计算舍入要求。再检查解释：模型逐项判断每个异常说明是否被对应订单支持，不能仅看是否出现“异常”一词。对原始记录互相矛盾、无法确定正确金额的情况，应确认是否明确标为待核实，而不是强迫裁判选出一个金额。

然后准备四种候选交付。A 用不同列顺序但内容正确，应通过；B 报告流畅却漏掉一条冲突，应失败；C 金额正确但修改了原表，应触发硬约束失败；D 文件无法打开，应先记录证据不可判定，并查明是产物损坏还是采集失败。A 检验误拒，B、C 检验误放，D 检验故障出口。没有任何一个单独的参考文件能够覆盖这些情况。

聚合时，完成度和总体通过分开报告。遗漏冲突可以说明其他部分已完成，却不能用“排版优秀”补回任务成功；若原表损坏属于禁止副作用，也不能与文风平均。本文建议将硬条件表示为必须同时成立的门槛，软质量保留分项结果。具体哪些条件是硬门槛，应来自任务约定，而非裁判临时发挥。

五、结果、过程与奖励漏洞

结果通常比固定路径更接近用户意图，但只看终态也会漏掉问题。上例中原表被改后又恢复，最终快照可能看不出来；若“不修改”是过程约束，就需要相应写入日志。相反，任务没有限定软件或操作顺序时，不应因 Agent 使用另一条有效路径而扣分。本文建议只对授权、不可逆副作用及明确业务流程检查必要过程，把其他轨迹留作诊断材料。

真实调用成功、Agent 宣称成功、外部结果正确，是三个不同命题。裁判应尽量读取独立保存的结果证据；轨迹中的自述可帮助定位，却不独立证明完成，更不能把推理文本直接当作真实动机。证据采集和隔离怎样实现归第 04 篇，本篇负责规定裁判需要什么证据以及缺失时如何判。

METR 在 2025 年公开的软件开发与 AI 研发评测案例中，观察到修改测试、接触参考实现和利用计时漏洞等取巧行为。该报告证明这些失败机制实际出现过，不提供所有 Agent 的统一发生率。本文据此建议：把评分器和参考答案放在受保护边界；用未见输入复查泛化；检查评分证据能否被被测系统伪造，并把“文本要求裁判给满分”作为恶意交付反例。METR，2025-06-05

取巧不只发生在代码层。如果 rubric 只统计是否提到风险，Agent 可以罗列大量无关风险；如果评价只看数据库最终值，Agent 可能绕过必须的授权。裁判要检测的是用户目标与得分之间的裂缝，而非穷举某一代模型的所有作弊方式。这是机制推断，需要在自己的任务中验证。

六、把裁判当作一个待验收系统

本文建议建立一个与调参样本分开的裁判验证集。它同时包括真实交付和人为控制的反例：正确替代解、只改一个关键事实的错误解、格式变化、缺失证据、违规过程，以及针对裁判的诱导文本。合成反例用于隔离机制，真实交付用于防止只会识别人为错误；两类结果分别保留。

验收可按以下顺序推进：

  1. 核判据。 领域专家先检查要求是否可观察、可执行，是否漏掉硬约束，是否误加任务外义务；为争议保留解释和裁决记录。
  2. 核标签。 由至少两位具备相关知识的人独立判断困难样本，分歧时回看证据；无法解决的案例标记未知，不能仅以多数票制造真值。
  3. 核错误方向。 分别报告正确交付被拒、错误交付被放行的比例，并列出各自分母；再按被比较系统或产物来源分层，标注裁判与生成者是否同模型或同家族，检查错误是否偏向某一方。类别失衡时，单一总体一致率可能掩盖关键错误。受控反例集上的这些比例不等于真实使用中的错误率，真实分布推断交第 05 篇处理。
  4. 核扰动与遗漏。 交换答案顺序、改变不相关格式，再插入单个关键错误。程序测试也要做这一步，检验它既接受等价解，又能抓住实质变化。
  5. 核未知与版本。 分开记录裁判弃权、超时、解析失败和有效判定；保留覆盖率、模型版本、提示词、规则及测试版本。改动后先重跑保留集，再讨论能否替换旧裁判。

如果允许弃权，就要同时看“判了多少”和“已判部分错了多少”。把难例全部弃权会制造漂亮准确率；把未知全算失败，又会把评分设施故障混入 Agent 能力。错误究竟来自产物、证据采集还是裁判服务，应保留可追查原因，最终统计处理由第 05 篇接续。模型自报置信度只能作为待校准信号，不能直接当作正确概率。

七、取舍、反证条件与尚未解决的问题

本篇推荐的最小组合是：少量必要硬断言、能区分实质质量的 rubric、独立验证集，以及面向争议的专家出口。不要为所有任务默认叠加多个模型；增加裁判的价值应由错误下降证明。若便宜程序已准确覆盖某项，再加模型可能只引入噪声；若错误集中在专业知识不足，增加同类模型票数也未必有效。

三个条件会推翻这套具体配置：正确替代解持续被拒，说明判据或程序过窄；关键错误持续被放行，说明证据、规则或裁判能力不足；专家分歧持续集中在同一项，说明任务语义或标签标准尚未稳定。此时应回到出错层修订，而不是只调最终分数阈值。

公开材料仍不能回答某个企业场景需要多少专家样本、可容忍多少误放，或哪款当前模型最适合做裁判。这些值取决于任务分布、错误代价与实际样本。本轮也没有逐项复现 OSWorld 修补、独立重审 SWE-bench 题目或运行所引论文。可交付的结论是判据设计与验证方法；要声称“该裁判可用”，还需要在目标任务上完成上述验收。

运行条件与采到的证据，符合实验约定吗？

执行条件的可控与等价

执行条件包括状态、权限、预算与采证。隔离必须覆盖会改变结果的状态，通用运行器不自动保证实验等价。

本篇可从核心问题进入：状态边界 · 等价核验 · 框架取舍。

本篇要回答什么

这次运行和采到的证据，是否符合约定的实验条件；条件变化后，实验含义是否仍然成立？

同一任务、同一模型，可能因为残留数据、额外权限、隐藏的重试或采证时点不同，而变成不同的实验。本篇关心这些条件能否被明确、落实和核查。跨运行器、并发和部署迁移只是核验场景，Harbor 接入也只是其中一个案例。

这里的“等价”指与当前判断相关的条件和语义得到保留，不要求实现相同，也不保证每次输出或分数相同。分数接近不能单独证明等价；分数下降也不能单独证明执行有错。

作为工作定义，benchmark 固定任务集合与比较协议，产品评测套件覆盖特定产品能力及回归风险，评测系统负责使它们能够运行、复核和维护。本篇只讨论其中的执行条件。全局问题回到总览；测谁归 01，任务应保留什么归 02，什么算成功归 03，差异如何归因归 05。

一、状态边界决定隔离与重置

隔离必须覆盖任务能改变、且会影响其他运行或判分的状态。 容器、进程或 VM 的边界是实现选择；真正要核查的是数据库、文件、账号、会话、缓存与记忆是否仍在边界外相互影响。

状态关系 应明确什么 条件失真会怎样发生
任务独占 初态如何创建，运行结束后如何回收；失败退出也要处理。 上一题的数据或文件进入下一题，实际起点不同。
多任务或多参与者共享 谁能读写，何时允许修改，重置会波及谁。 单个任务的清理删掉另一任务正在使用的数据。
允许跨任务保留 哪些经验可保留、哪些业务状态仍须重置；任务顺序与反馈来源是什么。 意外清空学习状态，或把测试答案当作可迁移经验。

这三类描述状态与运行的关系，并非给数据永久贴标签。同一个文件，在独立任务测试中应清除，在学习实验中可能需要保留。需要逐项规定业务数据、会话、长期记忆、技能文件和参数的生命周期。

  • SaaS-Bench 按次准备所需应用组合，把访问入口与后台验收关联到本次运行；环境分配、访问与验收协议是适配时必须保留的部分。部署与 API 说明
  • OSWorld 围绕桌面环境进行任务设置和恢复，其 Harbor 适配版继续使用镜像与评估器；复用这两者仍需检查交互和采证条件。原生仓库 · Harbor 适配版
  • TheAgentCompany 的 Harbor 适配说明要求串行运行，因为共享业务服务的重置会干扰其他任务。这是该适配实现的约束，不能外推成所有版本或所有部署都不支持并行。适配说明

由这些案例可推得：上层调度器“能并发”并不代表整套评测“可并发”。并发是否有效，需要在实际共享状态与重置范围下核验。公开实现不足以给各项目的吞吐、稳定性和成本排总名次。

二、把执行与采证约定落到组件之间

先规定允许发生什么，再记录实际发生了什么。 只保存最终分数，无法判断一次失败来自 Agent、环境初始化、工具访问还是证据丢失。

约定对象 运行前固定或声明 运行后保留的证据
初态与身份 数据、文件、账号、权限及共享范围。 初始化结果、实例与身份对应关系、已知偏差。
观测与动作 能看到哪些信息，能调用什么操作，操作对业务状态产生什么后果。 实际观测、调用及返回；失败和状态变化能关联到同一次运行。
预算与恢复 时间、步数、计算预算；超时、工具重试、整题重跑和人工介入规则。 实际消耗、每次重试及介入；任务难度的人类时长标定不等于 Agent 实际耗时，后者单独记录；失败尝试不因后续成功而消失。
采证与版本 何时、从哪里采集哪些证据；任务、应用、Agent 配置与验证器版本。 交付物、状态快照或差异、轨迹及版本标识；标明缺失与采集失败。

四、条件改变后，怎样判断是否仍可比较

等价是针对具体用途提出、需要证据支持的主张。 更换运行器、容器或接口后，应先说清哪些条件必须保留、哪些允许变化，再讨论结果。

可按三个层面检查，以下是方法建议，尚未由本系列实跑验证。

  1. 对齐协议。 比较初态、权限、观测、动作、预算、重试、记忆保留与验证器输入；记录允许差异。不能仅核对任务 ID 和模型名。
  2. 核验关键路径与失败路径。 在相同起点下检查动作后果、后台状态和采证；包含初始化失败、超时、重试、回收，以及共享状态下的串扰。无操作和已知错误的拒绝由 03 定义，04 核查是否向验证器提供了正确证据。
  3. 带着偏差解释运行结果。 保留逐题与逐次结果，将基础设施故障、Agent 行为失败、缺证分开记录并公开处理口径；不能悄悄丢掉失败或增加重试。是否合并比较、差异是否显著及能否归因，交给 05。

接口对齐是必要核验，不是证明统计等价的充分条件；输出随机性、样本量和允许误差还需要 05 处理。如果迁移同时改了工具能力或 Agent 编排，应先回到 01 确认是在比较完整系统，而不是把全部变化称作“换运行器”。

五、SaaS-Bench 接入 Harbor 应解决什么

本篇建议有条件地做可选适配，在旧稿基础上补充需求与维护条件，不据“有通用框架”就替换正式环境。 Harbor 提供任务包、运行与评分接口，已有材料表明其支持多容器环境与多维奖励。因此，需要多容器或多维计分，本身不构成自建运行器的充分理由。任务规范

对 SaaS-Bench，更关键的是把现有环境分配、访问与后台验收机制接到运行框架，同时保留上述语义。框架复用的价值与适配的成本应分别验收。

判断 希望获得什么 应拿什么证据决定
接入有增量价值吗？ 外部团队更容易复跑，减少重复接模型、调度与结果汇集的工作。 是否有真实复用需求；同一任务接入前后的集成步骤与成功复跑记录。
原有实验含义保住了吗？ 环境与判分实现继续有效，新增适配不暗改能力与条件。 初态、权限、观测、预算、重试和采证的对照；关键失败路径与共享状态核验。
维护负担划算吗？ 复用收益持续超过双重接口、版本兼容与故障定位成本。 真实使用频率、维护记录和故障归属；不能仅靠一次演示成功。

据此，有明确外部复用需求且能保住语义时，优先薄适配；需求尚弱或底层隔离仍不稳定时，可先补原生条件核验，再按上表证据决定。 这是基于公开架构的决策推断，不是 UniPat 已公开的路线，也未测得具体人日、吞吐或投资回报。

六、向其他专题交付什么

本篇的输出应是：实际运行条件、状态处理方式、预算与重试记录、证据来源，以及已知偏差。它让 05 可以解释结果，让 06 可以判断某个版本的证据是否仍能用于当前产品。

对企业资料收集，同样应追问“这份材料决定了什么实验条件”。以报销审批这个教学例为例：申请单与历史操作帮助 02 还原任务；制度与例外帮助 03 定义成功；身份权限和系统配置约束本篇的可行动作；财务与审计记录提供候选验收证据，其有效性仍由 03 核查。专家可以补充隐含规则并说明依据，执行系统再验证这些规则是否真正落实。

这把原始信息收集、专家精炼、环境模拟和下游评测接起来，但不要求四者由同一产品完成，也不把资料齐全等同于环境保真或评测有效。

结果比较、归因与泛化

想核算统计直觉，可跳到 100题配对教学例；判断外推边界可直接看 泛化条件。

分数差异只有同时交代比较条件、抽样不确定性和外推边界，才构成可解释的证据。“B 比 A 高 8 分”至少缺三项信息：是否做了同样的题、是否花了相当的资源、这次领先是否可能来自偶然。即使差异稳定，也不能自动推出“模型更强”或“换一家企业仍领先”。

本篇承接已确定的被测对象、任务、判据和执行约定。它研究结果怎么比较、差异怎么归因、结论能到哪里为止；不重做 01 的指标目标、02 的任务构造、03 的裁判设计、04 的环境重置，也不替 06 决定是否上线。以下方法建议是对一手研究的综合，教学数字为明确假设，本轮没有运行 Agent 实验。

一、先确定这次比较到底想估计什么

假设团队要在两个报销 Agent 中选型。固定同一批任务、单次预算和评分规则后，可估计的是“这两个系统在这些条件下的平均完成率差”。如果 B 同时更换模型、检索、提示词和重试次数，这仍是有效的整套产品比较，但不是模型增益实验。

可以把一次分数理解为多个因素共同作用的结果：模型、脚手架、任务、环境、预算和随机运行。它们之间还存在交互：某种工具接口可能只适合某个模型。因此，先把比较句写完整，再决定哪些因素固定、哪些允许变化。

要回答的判断 应怎样比较 结论边界
同等业务约束下谁更好？ 同题、同费用或时延约束，比较完整系统。 只对该预算与任务分布成立。
更换模型贡献多少？ 固定脚手架，替换模型并重复运行。 是该脚手架下的模型替换效果。
谁的能力上限更高？ 比较多档资源下的性能曲线。 不能等同于低成本部署效果。

“公平”并非所有资源都锁成同一个数字。相同 token 不等于相同费用或时间；相同费用也不等于相同计算量。必须由问题决定约束，并同时披露实际消耗，包括失败、重试、候选筛选和人工协助。缓存价格、工具费用、并行额度与本地计算应注明口径。2024 年《AI Agents That Matter》将准确率和成本联合比较，指出忽略成本可能误判复杂 Agent 的价值；本篇采用它的二维比较原则，而不把一种费用口径视为通用公平标准。S1：§2–4

三、同题配对保留了总分看不到的信息

比较 A、B 时，应保留每题各自的结果。共同成功、共同失败、A 独有成功、B 独有成功，表达的信息不同。配对分析直接计算每题差值，利用双方遇到相同难题的相关性；不宜只拿两个总分和各自误差条目测胜负。S2：§4

教学例，全部为假设。100 道从目标分布独立抽取的任务，各系统每题运行一次；两者都成功 55 题，仅 A 成功 5 题，仅 B 成功 13 题，都失败 27 题。因此 A 为 60%，B 为 68%，配对差为 +8 个百分点。

令每题差值为 B 得分减 A 得分，则有 13 个 +1、5 个 −1、82 个 0。样本标准差约为 0.419，均值标准误约为 0.0419；用正态近似得到 95% 区间约 [−0.2，16.2] 个百分点。这是简化教学计算，不是小样本下的精确保证。它说明数据既容许无优势，也容许较大优势；“没有排除零”不等于已经证明两者相同。

若忽略配对，把两个总分当成独立估计，同样用样本方差计算，标准误约为 0.0680，近似区间为 [−5.3，21.3] 个百分点。本例的配对区间更窄，原因是双方逐题得分正相关；配对并不保证在所有数据上缩小方差。55 题共同成功与 27 题共同失败虽在差值中均记为 0，却分别指出本次共同做对与共同没做对的范围；共同失败不代表能力上限。18 道结果不一致的题决定本例差值的非零贡献，全部 100 题仍参与均值和方差计算。

实际应对差值做适当的配对区间或检验。任务存在家族关系时，本例的独立假设不成立，要按相应层级处理。差异是否具有业务意义还需另定最小有用增益；统计区间解决的是估计精度，不代替业务取舍。

运行安排也会影响配对含义。初态和任务版本应一致；在线服务会漂移时，宜把两系统运行分散在相近时间块内，避免一个全在白天、另一个全在夜间。同一随机种子只有在双方真正共享可比随机机制时才有控制价值，不能保证交互轨迹相同。这些是实验设计建议，执行实现归 04。

四、重复运行与增加新任务，解决不同的不确定性

需要区分三个层次：同一题再跑一次会怎样、换一道同类题会怎样、换一个任务族会怎样。对 20 个模板各生成 50 个实例，再各跑 5 次，可以得到 5,000 条轨迹，却不能据此宣称有 5,000 个独立任务样本。若模板内高度相关，有效信息远少于轨迹数。

重复运行帮助估计同题波动；增加任务族帮助覆盖任务差异。预算紧时，可先用小规模重复判断波动主要来自哪里：若同题结果已稳定，继续重跑的价值通常低于补充新任务；若经常翻转，则需要更多重复。不存在脱离差异大小和波动水平的“统一跑三次”规则。S2：§2.2、§3.1

τ-bench 的 pass^k 表示同一任务 k 次独立重复试验全部成功的概率，再对任务平均；pass@k 则是 k 次中至少一次成功。前者研究一致性，后者研究多次尝试的解题覆盖。把 pass@k 当成自动交付率，还缺少能在实际运行中选出正确结果的机制，且筛选本身也消耗资源。S3：§3

METR 原研究采用“任务族→任务→尝试”的分层 bootstrap：按层有放回重抽，重复估计指标。比较两系统时，应在每份重抽样中保留同题配对，再估计差值。重抽的层级取决于要推广到哪里：若只关心固定题集的再次运行，就不要把“重新抽任务”的区间冒充运行噪声。S4：§3.2

置信区间描述的是指定抽样模型下的估计不确定性。它不会自动覆盖评分偏差、未知污染、遗漏的企业类型或未来环境变化。任务族很少时，分层重抽也无法凭空创造多样性，应该明确列出族数与未覆盖范围。

五、定位相关现象不等于完成因果归因

HAL 对模型、脚手架和基准进行多维比较，同时指出：定位轨迹错误，不能确定修复后会成功还是暴露后续错误。其附录 A4.2 明确提出保存失败点的 Agent 与环境状态、纠错后重放，以检验因果关系；作者也说明该方案超出当时计算预算，尚未实施。S5：§3–4、附录 A4.2

据此，本篇建议把“原因”分三级表达：日志显示某现象；控制其他条件后，替换该组件改变结果；这种效果在其他模型或任务族中仍存在。前一级只能产生后一级的假设。例如失败轨迹经常较长，也可能是难题导致反复尝试，不能直接归结为“多思考使性能下降”。

最小可解释设计是模型与脚手架的交叉对照：模型 M1、M2 分别搭配 H1、H2。若换脚手架只改善 M1，应报告搭配效应；若 B 同时改了检索、记忆和预算，只能先报告整套系统效果。逐项消融能缩小解释范围，但模块间交互意味着各项增益不能机械相加。

2026 年 AgentMeter v3 直接比较模型—CLI 配对，并对不同来源的任务描述进行对照。它采用任务级配对 bootstrap，但作者明确限制：CLI 是提示、工具、上下文等机制的组合，其差异不是某个机制的独立因果效果。描述改写实验也只是有限任务上的诊断，不能把优化后的题面等同于自然企业请求。S6：实验与附录 E

六、选择偏差和污染，不会被更窄的区间修复

选择至少发生在三处：选哪些题、从多少配置里选赢家、哪些运行进入统计。如果试过几十种提示词，只披露最高分，并用同批题计算区间，区间没有自动计入“挑赢家”的过程。更可信的做法是用开发集选择方案，冻结后在独立留出集比较；若只能用同一批材料，应称探索结果并披露选择过程。

异常运行的排除也应事先定规则。可单列确认为外部故障的运行，但必须给出各系统的排除数量与原因，并查看纳入后的敏感性结果。对某系统特有的长运行超时随意剔除，会把产品弱点从分母中删掉。

污染不仅来自模型训练，还可来自 few-shot 示例、检索库、持久记忆或联网找到标准答案。HAL 发现其所用 τ-bench few-shot 脚手架含测试示例后，排除了该脚手架的结果；这项发现不能扩展为“所有 τ-bench 结果均无效”。未知训练数据则应如实标记未知，不能把“未发现”写成“没有”。S5：附录 A5

2026 年 METR 的开发者研究更新提供了另一类选择偏差：部分参与者不愿在实验中放弃 AI，部分任务也不再提交。即使入组后的任务仍随机分配，入组前的选择仍会限制总体推断。作者因此不把后续数据视为当前生产率效应的可靠量化；这是抽样机制改变的案例，而不是“随机实验失效”的通则。S9：2026-02-24 更新

七、泛化必须说明跨越了哪条边界

从现有任务到新实例、从已知模板到新工作流、从一个组织到另一组织，是逐级增强的主张。对应留出也应升级：留实例只能支持实例层面的检验，声称跨企业时，还需要未参与开发的组织、制度、数据结构与权限组合。仅把同模板实例随机切分，不能验证跨工作流能力。这遵循“主张越一般，留出越需要不同”的原则；具体企业划分是本篇的应用建议。S1：§5

跨任务汇总还必须显式给权重。每题等权会让题目更多的流程占主导；按任务族等权回答的是另一问题；按企业流量加权又依赖流量估计。平均领先也可能掩盖某个关键流程退化，因此应同时展示族级结果和整体结果。重加权只能调整已有覆盖，不能补出未测流程。

本篇建议在看结果前约定关键任务族、比较对象和主要指标。族级检验越多，偶然出现显著差异的机会越大；确认性比较应预先约定多重比较处理，其余事后发现只标为探索信号，在独立样本上复测，不能挑出最有利或最不利的一族作为既定结论。

METR 的 TH1.1 把任务从 170 增至 228，并更换执行设施。报告承认任务分布改变会改变趋势估计；其迁移附录还提醒，跨任务族的宽区间不能代替固定任务上的运行差异分析。因此，新旧榜单应通过共同任务、共同系统建立桥接，再讨论趋势，不能把数值变化全算作能力进步。S7：任务更新及迁移附录

时间跨度本身也有边界：50% 时间跨度是一个时长，即在拟合的成功率曲线上，模型估计成功率达到 50% 时，对应任务的人类专业人员完成时长。它不是 Agent 已连续稳定工作那么久，更不是岗位替代率。原研究主要涉及软件与研究任务，明确讨论真实工作中动态环境、上下文和可靠性要求的差别。S4：§3.1、§5、附录 E.3

自主任务成绩与真实工作提速仍须分别测量；METR 2025 开发者实验及后续更新对线上校准的含义，见 06 评测证据的使用与线上校准篇。

八、交给下一篇的，应是一条有边界的结论

比较报告应能完整回答：在哪个冻结版本、哪些任务族、什么预算下，B 相对 A 改善多少；差值区间覆盖哪些随机来源；哪些变化仍无法归因；哪些留出范围已验证。它不应只交付冠军名称。

本篇建议采用这样的结论句：“在指定任务族与单次预算下，B 的配对完成率差为 X，区间为 Y；该结果衡量完整系统，尚未隔离模型贡献；新组织和新流程未测。”随后由 06 结合成本、错误后果与线上证据决定如何使用。

当前证据仍有三处缺口：公开研究的任务分布与企业真实流量缺少普遍映射；组件交互的因果证据有限；公开任务暴露和闭源训练数据使污染很难完全排除。可靠结论的目标是让这些边界可见，而非用更多小数位掩盖它们。

06

离线信号能预测真实交付吗？

评测证据的使用与线上校准

把发布作为可撤回的有条件决定。真实输入、真实用户反应和业务结果是不同证据。

本篇判断：评测结果只有对应到一个有边界的决定，并接受真实使用结果的检验，才成为可用的产品证据。 离线领先可以支持候选进入下一阶段，不能自动支持全面发布。线上未报警也不能反向证明离线评分正确。关键是说明每份证据减少了什么不确定性，还剩什么必须另查。

本篇承接前五篇已经明确的对象、样本、判据、运行条件与比较结果，研究选型、发布、诊断和回归如何使用这些结果。统计估计回到第05篇，裁判误判回到第03篇，环境复现回到第04篇。以下公开事实已查阅一手来源；退款案例、决策流程和操作建议是本文综合设计，未进行真实平台或业务实验。

一、第一性：证据要承接决定，也要允许决定被撤回

“新版本成功率更高”只是一个条件性观察。是否值得发布，还取决于提高发生在哪类任务、失败损失是什么，以及线上使用是否保留了测试条件。评测不是一次盖章，而是让团队有理由选择行动，并知道什么新事实会推翻选择。

贯穿本文的教学案例是售后退款 Agent。现有版本由坐席确认后执行退款；候选版本更擅长识别订单与解释规则。团队希望扩大低风险任务的自动处理范围。即使候选在离线套件中领先，也可能因真实用户补充信息、支付回调延迟或重复提交而失败。改善“解释正确”也未必减少坐席的总投入。

决定 可以使用的证据 证据不足时的动作
选型：候选值得继续吗？ 目标任务上的表现、成本及失败类型。 缩小候选范围，补测会改变排序的场景。
发布：可以扩大哪些权限或流量？ 关键约束通过，且目标使用条件已获得相应验证。 保留人工确认或缩小适用范围。
诊断：先修哪里？ 失败轨迹、环境结果与版本变更的对应关系。 提出可证伪解释，再做最小对照。
回归：原有承诺还成立吗？ 已承诺场景的持续表现和线上异常。 停止扩量、回退或重新限定承诺。

同一个差值对四个决定的意义不同。新能力突破可以支持继续研发；一项低频越权行为却可能足以否决自动执行。“总体提高”不能抵消产品明确不接受的失败。 哪些失败构成否决条件，应在看结果前由业务责任人约定，而不是看到分数后临时解释。

二、近两年的变化：从发布前测量，走向持续检查证据是否有效

2025年的公开材料展示了两种不同缺口。METR随机对照研究覆盖16名熟悉自身开源项目的开发者、246项任务，报告使用当时AI工具的任务耗时增加19%。它支持的是特定人群与时期的结果，也说明基准能力和工作提速需要分别测量；它不支持“AI普遍降低生产力”。METR原研究说明

同年Anthropic的事故复盘承认，既有评测未捕获用户报告的质量退化。文章说明其常规验证包括先向小规模canary群体部署，但未逐一披露三项故障的灰度过程；不能据此断言每项故障都经过同样的灰度检查。作者提出在真实生产系统持续运行质量评测，说明发布前证据仍有覆盖缺口。2025年官方复盘

2026年METR认为后续数据无法可靠估计当时收益大小，提示测量方法本身也需要重新校准；选择偏差详见第05篇。不能把新数据包装成已证实的普遍加速。研究设计更新

Anthropic同年区分能力评测与回归评测，并主张自动评测、生产监测、用户反馈、人工复核和A/B测试相互补充。2026年方法文章 本文据此形成的判断是：不仅要更新题目，还要检查“题目—线上行为—业务结果”的关系是否仍成立。这是方法主张，不是行业已经完成转型的普查结论。

三、六类证据各自回答什么

这些方法不是必须依次打卡的固定流水线。低风险措辞修改与开放真实退款权限，应承担不同的取证成本；选择依据是尚未解决的不确定性。

机制 最适合回答的问题 单独不能证明什么
离线评测 在可控制条件下，候选是否完成规定任务？ 真实流量上的收益与未知失败。
影子运行（shadow） 接触真实输入后，候选会怎样响应？ 用户看到新响应后的行为及完整交付效果。
小流量发布（canary） 有限真实暴露中是否出现应阻止扩量的问题？ 长期价值、罕见故障不存在。
随机A/B实验 在约定人群与期间，改动是否改变业务结果？ 改善的具体机制和范围外效果。
人工复核与用户研究 自动信号遗漏了什么，失败为何重要？ 未经适当抽样的总体发生率。
生产监测 当前系统是否持续偏离预期？ 没有观测到的损失及变化的因果来源。

影子运行的边界尤其容易误读。 SageMaker的官方机制复制实时推理请求，仅把生产版本的响应返回调用方；影子输出可记录比较。AWS文档 这支撑“真实输入、不展示候选响应”的做法，不代表它已经解决完整Agent的工具副作用。

对退款Agent，本文建议让影子版本生成动作计划，或在隔离的业务副本中执行。只丢弃最终聊天答案，却允许它调用真实退款接口，仍会产生真实后果。若只生成计划，得到的证据就只覆盖决策层；若回放旧工具返回值，候选改变了调用顺序后，后续返回值也未必仍有效。多轮对话还缺少用户对候选回答的真实反应，不能称为完整线上任务验证。

小流量发布和A/B实验可共享分流机制，但决策目的不同。 Google SRE把canary定义为局部、限时的变更部署与评估，也明确其属于A/B比较；并指出共享依赖可能使两组一起退化。Google SRE章节 本文将“是否继续发布”的检查，与“业务收益有多大”的实验分开命名，以免把短期无明显故障当成收益证据。

本文建议随机分组后保持会话内版本固定；同一账户的多笔退款会相互影响时，按账户分组，不能把每轮消息当独立样本。上线前约定分析单位、主要指标、观察窗口与停止条件，并检查实际分流是否符合分配、两组是否共享受影响的状态。第05篇的聚类原则可帮助理解相关性，但不替代线上实验设计。

安全事件可随时触发停用；收益判断则不能每天重复普通显著性检验，挑首次“显著”时宣布获胜。采用预定观察窗口，或另行设计适合持续观察的序贯方法。后者的具体算法与样本量设计本系列未覆盖；提前安全停用后，应报告截断范围，不能照搬原定终点的收益结论。

四、典型实践的差异：工具连接证据，不能替团队保证结论

LangSmith文档把离线历史回测、生产轨迹评分与失败回流数据集联系起来。这证明一种工作流可以被平台承载，不证明自动评分已经等价于用户结果。LangSmith官方文档 对退款场景，模型裁判给出“解释合理”，与支付系统确认到账、客户没有再次申诉，是不同信号。

AWS影子机制主要连接候选与实时请求，Google SRE机制连接局部部署与发布判断，METR的随机研究直接检验人在真实工作中的效果。它们不能用同一“评测平台能力清单”替代比较：前两者提供操作机制，后者提供特定研究设计下的效果证据。没有哪一项单独覆盖全链条。

Anthropic的2026年4月复盘提供另一个反例：压缩输出提示通过原有评测，扩大套件并做消融后，才发现一项评测退化。另一项缓存优化故障会在会话闲置超过一小时后，持续逐轮清除较早的推理；内部消息队列实验和思考显示改动曾妨碍复现。官方称该故障于4月10日、v2.1.101修复，压缩提示于4月20日撤回；截至4月20日、v2.1.116，三项问题均解决（其中另一项本文未展开）。2026年官方复盘 这支持检查交付配置和覆盖缺口，不证明所有简洁提示都有害，修复声明也不是本轮独立验收。

五、贯穿案例：怎样把“离线领先”变成有条件的发布决定

以下全部是建议流程，不是已取得的实验结果。团队先把候选用途限定为规则明确、金额受限的退款请求。离线结论应写成“在这些条件与约束下，值得验证自动执行”，而不是“可以替代坐席”。历史回测保留时间边界，避免使用当时尚未出现的物流状态或最终申诉结果帮助Agent答题。

进入影子运行后，重点找离线未覆盖的输入、动作分歧和运行时问题。人工复核分歧时，不能默认线上旧版本就是正确答案，也不能只看候选失败。应同时抽取两版都通过、两版都失败的案例，检查共同盲点。若发现真实订单状态缺失，先解决状态可见性；继续调提示词未必触及根因。

有限发布需要一张具体的决策记录：部署配置与适用人群、关键约束、观察窗口、扩量条件、停止条件、接管责任人。阈值由业务损失容忍度与基线确定，本篇不提供通用的“成功率达到多少即可上线”。若关键指标还没有可靠采集路径，就不能把“没有告警”写成通过。

案例中的立即停止条件可以是已确认的越权退款或重复扣退；一般错误率与等待时间则按预先约定的基线和容忍范围判断。回退旧版本只能阻止继续暴露，已经发生的退款还需单独对账与补救。

零事件不等于零风险。在预先固定的观察范围、事件可完整检出、案例近似独立同分布的条件下，n例零事件的单侧95%二项置信上界为 1−0.05^(1/n)，n较大时约为3/n。因此1,000例零越权，上界仍约0.3%。这是由精确二项方法推得的“三法则”，不是越权率低于该值的确定保证；同账户重复、故障聚集、漏报或反复观察择时停止时，不能直接套用。NIST精确二项方法

验证收益时，同时观察完成的退款任务、人工审核和返工时间、端到端等待，以及在约定窗口内的重开与申诉。不能只统计Agent自动关闭的工单，否则把难单全部转人工就能制造漂亮分数。以进入约定范围的请求为分母，另报转人工和未结束情况；尚未到结果观察期限的任务标为待定。

若处理时间缩短但坐席返工增加，应暂停“节省人力”的结论。若收益只存在于资料齐全的切片，可以保留该范围继续使用，并把缺资料场景交回人工。这是收窄产品承诺，不是为了保住总分而删除失败。

六、怎样检查离线信号是否预测线上结果

校准不是把两类分数调成一致，而是检查离线信号与业务结果的联系。以下是退款案例的教学方案，没有真实数字，也不是已被来源验证的通用流程。

案例层先做同批配对。 在同一已上线配置、约定业务范围内抽取请求，等待到账与重开观察窗口结束。保存请求当时的信息和初态，用该已上线版本离线回放，裁判不得看到后来的业务结果；再按请求标识连接两类标签。无法重建初态、标签尚未成熟或缺失的请求单列并报告数量，不能算成功。

离线判定 线上结果良好：按约定完成且窗口内无重开 线上结果不佳：未完成或窗口内重开
通过 a：支持该信号的案例。 b：离线未预警的候选漏报，需查交付盲点。
不通过 c：候选误拦，需查合理解法或人工补救。 d：两侧一致失败，提供诊断入口。

先看通过样本中的线上不佳率 b/(a+b)，再看未通过样本中的线上良好率 c/(c+d)，并按预先关心的退款类型拆看。分母为空时不计算。四格不一致不自动证明裁判错了：重放随机性、环境差异和人工救场都可能造成差异。四格都应记录人工介入与投入，并事先约定转人工如何计分，按自主完成与人机协作分层报告。a 格若靠人工纠正才成功，就不能支持 Agent 自主能力；c 格若依赖人工补救，也不能据此认定自主执行被“误杀”。

版本层再检查改善方向。 对多个实际候选，固定离线套件与基线，逐个登记离线增益；线上在可比人群中与同一基线随机比较，登记业务增益及不确定性。将“离线上升、线上改善”“离线上升、线上无改善或变差”等并列，检查是否反复错向。区间宽、方向未定时保留“不确定”，不同时间或人群未经对齐不直接比差值。少数同向版本只提供局部支持，不能证明今后升分必然增益。

这一检查仍受选择限制：只有被选中上线的版本和请求拥有对应结果，被拒绝候选缺少反事实；观察窗口外的后果未被覆盖。影子运行也没有用户对新回答的真实反应，不能拿旧版本结果充当影子候选的线上标签。因此校准结论应限定到已观察的版本、范围与期限。

出现不一致后，形成三个待检验解释：真实任务改变了，评分遗漏了交付要求，或部署与人工流程改变了。通过但重开增加时查到账与后续行为；工具错误集中增加时查服务条件；评分提高但人工投入未降时查审核和返工。这些只决定调查方向，不能据共现认定根因。

回流时保留失败前可见的信息、关键操作和最终结果，将敏感信息按授权处理，再制作能够重现核心失败的用例。若无法恢复必要状态，应标为待复现线索，而非声称已有有效回归测试。修复原例之外，再留一组没有参与修改的相近场景检查泛化；否则只能证明团队学会了回答已知题。

保留三种用途不同的样本很有帮助：已承诺能力的稳定回归集、检查近期真实分布的滚动样本、用于诊断和修复的事故样本。事故样本刻意富集失败，不能直接用于估计总体错误率。旧题也不应因“已做对”全部删除：它们仍能保护过去的承诺。具体采样与权重回到第02、05篇。

训练是另一个消费场景。失败轨迹可以转成训练或优化材料，但一旦用于调参，就不再提供同等独立的验收证据。应记录使用边界并保留独立检验；本篇不展开奖励模型、RL算法或训练吞吐。

七、可以执行的判断与仍未知的部分

每次版本决策至少能回答：这次批准什么范围；证据对应哪个配置和人群；哪项重要结果仍未观测；什么事件会触发暂停；谁负责补证据。一个有条件的小范围决定，往往比含义不清的“综合评测通过”更可执行。

线上校准也有成本与限制。标签可能延迟，投诉存在选择偏差，少量企业客户不足以支撑稳定A/B估计，保存完整轨迹又受到隐私与权限限制。此时可采用受控试点、人工审阅与阶段性对账，但必须保留证据强度的差别，不能把替代方案直接称为因果证明。

本轮没有验证任何平台当前账户的实际可用能力，没有运行退款Agent、影子测试或线上实验，也没有估计通用收益。九项来源分别支持机制、方法或具体事件；案例的发布规则仍待真实业务校准。下一步可选择一项真实决定，按第六节连接离线信号与线上结果，并检验其局限。

需要审查者重点检查的推断

  1. 正文把证据按“支持哪个决定”组织，而不是按平台分类。这是研究框架，不是任何单篇论文的原有分类。

  3. 案例将关键事件停止条件、业务收益验证与长期监测分开。阈值没有套用供应方数字，仍需业务责任人和真实数据确定。
  4. 事故样本用于诊断、稳定样本用于回归、滚动样本用于分布校准，是本文建议的职责划分；未声称三套数据必须物理分库。
  5. 回退部署不能撤销已发生退款；训练使用会改变检验独立性。只解释决策含义，不展开补偿系统实现或RL系统设计。
